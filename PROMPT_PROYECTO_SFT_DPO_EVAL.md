## 1. Project goal

Build an end-to-end **evaluate → synthesize data → align → re-evaluate** loop:

1. Take a small open instruct model.
2. Define a written **policy** for a regulated domain (medicines / health information).
3. Generate **synthetic** SFT data and **preference pairs** that encode the policy.
4. Fine-tune with **SFT (LoRA)**, then **DPO** on top.
5. Compare **Base vs SFT vs SFT+DPO** with a statistically rigorous, bilingual (EN/ES) evaluation, including validation of the LLM judge against my own human labels.

Working title: `policy-alignment-eval` (suggest a better name if you have one).

## 2. The policy (domain: health/medicines information)

Draft `policy/policy_v1.md` with me before generating any data. Starting point:
- **MUST help** with general, educational medical/pharmacological information (how a drug class works, what a clinical trial phase is, what an EMA EPAR is, general side-effect info from public labels).
- **MUST NOT** give individualised dosing, start/stop/switch advice, or diagnosis for a specific person → instead give general info + clear referral to a healthcare professional/pharmacist.
- **MUST NOT** fabricate regulatory status, approvals or citations; express uncertainty when unsure.
- **MUST** answer in the user's language (ES or EN).
- **MUST NOT over-refuse**: refusing harmless educational questions is a policy *failure*, not a safe default.

The two failure modes — **unsafe compliance** and **over-refusal** — must both be measured throughout.

## 3. Technical constraints

- **Base model:** `Qwen/Qwen2.5-1.5B-Instruct` (Apache-2.0). Keep the code model-agnostic via config so I can swap to a 0.5B model for fast iteration or a 3B model if compute allows.
- **Compute:** free Colab T4 / Kaggle T4×2 (16 GB). Use **LoRA** (PEFT); QLoRA 4-bit as fallback. Training code must run as Colab/Kaggle notebooks that call the `src/` package; do NOT try to train inside this local environment. Local machine is a Mac — local runs only for data, eval and stats.
- **Libraries:** `transformers`, `trl` (SFTTrainer, DPOTrainer), `peft`, `datasets`, `accelerate`, `bitsandbytes` (optional). Pin versions in `pyproject.toml`; use `uv` or plain `pip`.
- **Synthetic data + judge:** a stronger LLM through an API, provider configurable (Anthropic / OpenAI / AWS Bedrock). Keys via `.env`, never committed. Cache every API call to disk (hash of prompt + model + params) so reruns are free and reproducible.
- **Seeds and configs:** everything driven by YAML configs in `configs/`; log seeds, model revisions (commit hashes), and library versions with every run.

## 4. Data

`data/` pipeline, step by step:
1. **Seed prompts:** ~60 hand-written seed questions (I'll review them) across 3 buckets — `should_help`, `should_redirect`, `borderline` — in EN and ES.
2. **Expansion:** LLM-generated paraphrases/variations to ~1,500 prompts, balanced across bucket × language. Dedupe (MinHash or embedding similarity) and filter.
3. **Held-out test set:** ~300 prompts **created separately and frozen before any training**, never used for generation or tuning. Size justified by the power analysis in §6. I will human-check every test prompt.
4. **SFT data:** policy-compliant responses generated by the strong model with the policy in the system prompt, then filtered by an automatic policy check.
5. **DPO pairs:** `chosen` = policy-compliant; `rejected` = one of two deliberately produced failure types: (a) unsafe compliance, (b) over-refusal. Keep a `rejection_type` column — I want to analyse which failure type DPO fixes.
6. Data card (`data/README.md`): sources, generation prompts, filters, counts, known biases, licence.

## 5. Training

- `notebooks/01_sft.ipynb`: SFT with LoRA (sensible defaults: r=16, alpha=32, lr≈2e-4, 2–3 epochs, max_seq_len 1024 — justify or adjust). Track train/eval loss.
- `notebooks/02_dpo.ipynb`: DPO from the SFT adapter (beta≈0.1 to start; compare 2 betas if time allows). Track reward margins / chosen vs rejected log-probs.
- If compute allows, **3 seeds per configuration** so I can report training variance, not just eval-sampling variance. If not, state it as a limitation.
- Save adapters; optional push to Hugging Face Hub with a model card.

## 6. Evaluation — this is the core and must be done with rigor

Systems: `base`, `sft`, `sft_dpo` (× seeds). Greedy decoding for the main results; fixed generation params logged.

**Dimensions (per response):** policy compliance, helpfulness, over-refusal (binary), unsafe compliance (binary), language fidelity (binary), factual-hallucination flag.

**Judge:**
- Rubric-based LLM-as-a-Judge with explicit criteria per dimension; prompt versioned in `eval/judge_prompts/`.
- Also a **pairwise** judge (sft_dpo vs sft, sft vs base) with **both orderings** to measure and cancel position bias; report the order-inconsistency rate.
- Judge must be a different model family from the one used to generate training data where possible (to limit self-preference bias); document the choice.

**Judge validation against humans:**
- Build a small labelling tool (a simple CLI or Streamlit page) so I can label a stratified sample of ~150 responses blind to system identity.
- Report judge–human agreement: Cohen's κ (binary dims), weighted κ or Krippendorff's α (ordinal), with bootstrap CIs. Report results separately for EN and ES.
- If agreement on a dimension is poor, say so and down-weight / exclude that dimension in the conclusions.

**Statistics (`src/stats/`; if I already have my own stats-eval package, use it as a dependency instead):**
- **Power analysis before running the final eval:** what test-set size is needed to detect a 5–10 pp difference in compliance rate with paired data at α=0.05, power=0.8? Document it.
- Paired comparisons per prompt: **McNemar** for binary outcomes, paired permutation / Wilcoxon for scores.
- **Bootstrap 95% CIs** (resampling prompts; cluster by seed prompt family to respect paraphrase dependence) for every headline metric and every difference.
- Correct for multiple comparisons (Holm) across dimensions × system pairs.
- Report **effect sizes**, not just p-values.
- **EN vs ES gap** for each system with CIs — does alignment transfer across languages?
- Breakdown of DPO effect by `rejection_type` (does it fix over-refusal, unsafe compliance, or trade one for the other?).
